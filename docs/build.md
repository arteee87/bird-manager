# Сборка и публикация

Пакет собирается одним скриптом из корня репозитория. Он же публикует результат в
apt-репозиторий; установку он не делает, пока её явно не попросят.

```sh
scripts/build-deb.sh                 # собрать и опубликовать
scripts/build-deb.sh --bump minor    # то же с повышением минорной версии
scripts/build-deb.sh --no-publish    # собрать, репозиторий не трогать
scripts/build-deb.sh --install       # ещё и поставить, дождавшись health
scripts/build-deb.sh --help          # полная справка (печатает шапку скрипта)
```

## Версия

Текущая версия всегда лежит в `VERSION`, последняя собранная — в `dist/.last_version`.
Скрипт решает сам:

| Ситуация | Результат |
|---|---|
| `VERSION` не менялся с прошлой сборки | патч поднимается на единицу, номер не переиспользуется |
| `VERSION` отредактирован вручную | берётся как есть и сообщается, чем отличается от прошлой сборки |
| `--bump patch\|minor\|major` | поднимается этот компонент, справа от него — нули: `1.2.3` → `1.2.4` / `1.3.0` / `2.0.0` |
| `--version X.Y.Z` | точная версия, она же записывается в `VERSION` |

Некорректная версия отвергается, а не собирается; `--bump` вместе с `--version` —
ошибка, а не тихий победитель. Проверка: строка должна состоять только из цифр и точек,
а после нормализации — не более трёх компонент. Короткая запись `X.Y` и `X` допускается
и дополняется нулями. Верхней границы для значения компоненты нет — сценарий отсекает
`abc`, `1.2.x` и `2.3.4.5`, но не ограничивает разрядность.

Арифметика версий закреплена тестами `test_build_script_resolves_versions_without_arguments`
и `test_build_script_bump_levels_are_correct` — второй вырезает из скрипта сами
вспомогательные функции и прогоняет их в настоящем bash, включая случаи переноса
разряда (`0.9.9` patch → `0.9.10`).

## Что попадает в пакет

```text
/usr/lib/bird-manager/app/            модули приложения, без __pycache__
/usr/lib/bird-manager/static/         css и js
/usr/lib/bird-manager/templates/      шаблон панели
/usr/lib/bird-manager/init_db.py      создание схемы БД
/usr/lib/bird-manager/requirements.txt
/usr/lib/bird-manager/VERSION
/usr/lib/bird-manager/.env            дефолты пакета (перекрываются /etc)
/etc/bird-manager/.env                conffile оператора
/lib/systemd/system/bird-manager.service
/usr/share/doc/bird-manager/          README.Debian, copyright
/usr/share/man/man8/bird-manager.8.gz
/DEBIAN/                              control, conffiles, templates, maint-скрипты
```

Тесты (`tests/`) и документация (`docs/`) в пакет не входят. Каталоги
`app/live`, `app/staged` и `app/apply_state.json` вырезаются даже если остались в
рабочем дереве: это артефакты прошлых прогонов, а не часть поставки.

Версия подставляется в два места: `Version:` в `control` и `.TH` в man page. В man page
подставляются также месяц и год, так что её заголовок не устаревает — держать версию
в исходнике руками не нужно.

Скрипт завершается выводом `dpkg-deb --info` и полного списка файлов пакета, поэтому
состав поставки виден сразу после сборки.

## Проверки перед публикацией

Сборка сама по себе не запускает тесты — это осознанно, чтобы быстрый цикл не платил
за полный прогон. Проверять стоит самому:

```sh
python3 -m pytest -q          # 282 теста
node --check static/js/app.js # синтаксис фронтенда
```

Сборка отдельно проверяет man page линтером `groff`, если он есть, и отказывается
собирать пакет с битым man page.

## Публикация

При `--no-publish` пакет остаётся в `dist/`. Иначе скрипт копирует его в пул
apt-репозитория и вызывает `/usr/local/bin/publish-repo.sh`, который пересобирает
метаданные:

```text
/srv/repo/pool/main/b/bird-manager/*.deb      пакеты
/srv/repo/dists/stable/main/binary-all/Packages{,.gz}
/srv/repo/dists/stable/Release
/srv/repo/dists/stable/Release.gpg           отделённая подпись
/srv/repo/dists/stable/InRelease             встроенная подпись
```

Каталог репозитория переопределяется переменной `APT_REPO_DIR`; скрипт публикации
должен лежать в `/usr/local/bin/publish-repo.sh`. Подпись делается тем же GPG-ключом,
которым клиенты доверяют репозиторию.

Так как stanza на каждый пакет в пуле попадает в `Packages`, в списке версий видны все
собранные пакеты, а кандидатом apt выбирает старший.

## Установка и апгрейд

```sh
sudo dpkg -i dist/bird-manager_<version>_all.deb
# либо одной командой со сборкой:
scripts/build-deb.sh --install
```

`postinst`:

- создаёт системного пользователя и группы, добавляет пользователя в группу `bird`;
- создаёт `/var/lib/bird-manager`, `staged`, `backup`, `live-bak` и `/etc/bird/live`;
- инициализирует БД, если её ещё нет;
- при отсутствии сгенерированных файлов засевает минимальный бандл;
- мигрирует старый управляемый блок в `/etc/bird/bird.conf` на стабильный include —
  с предварительным бэкапом и проверкой кандидата через `bird -p`. Кандидат, который не
  проходит проверку, не коммитится, а предыдущий файл восстанавливается;
- ставит `SGID` и права `0750` на каталоги бандла, `0640` на файлы;
- перезапускает службу.

**BIRD перезагружается только если postinst реально переписал главный конфиг.**
Обычный апгрейд кода этого не делает: `birdc configure` вызывается только при миграции.
`/etc/bird-manager/.env` — conffile, поэтому правки оператора переживают апгрейд, а
`postinst` лишь предупредит в лог, если в нём не хватает ключей доступа, и не будет
переписывать файл ради этого.

Удаление — `apt remove` (по умолчанию «нет») или `apt purge` (всегда полная очистка).
Разница описана в debconf-шаблоне `remove-all-data`: перед удалением живых файлов
управляемый include заменяется инлайновым сгенерированным конфигом, который затем
проверяется через `bird -p` и перечитывается.

## Откат

Откат публикации есть в самом приложении: снимок предыдущего бандла лежит в
`/var/lib/bird-manager/live-bak`, а полный бэкап (SQLite, live, staged, манифест,
главный конфиг) — в каталоге бекапов. Порядок и идентификаторы описаны в
[api_backend.md](api_backend.md).
