# API bird-manager

Документ описывает текущее поведение, а не конкретный выпуск: источник истины —
`app/routes.py`, а тесты `test_api_doc_lists_every_registered_route`,
`test_api_doc_matches_live_response_fields` и
`test_api_doc_include_order_matches_generator` сверяют этот файл с кодом. Номер
версии — в `VERSION`.

## Общие сведения

Стек: Python, SQLAlchemy/SQLite, custom WSGI router и waitress. JSON API не
использует аутентификацию; доступ ограничивается allowlist источников
(`BIRD_TRUSTED_SOURCES`), а `user_id` необязателен и по умолчанию `system`.
Web-операции отправляют значение `USERNAME` из `.env` (default `User`) только
как идентификатор журнала; права доступа этим не меняются.

Все временные метки в ответах (`timestamp`, `created_at`, `last_applied`,
`bird_last_*`) — локальное время машины, на которой запущен сервис. UTC не
используется.

```sh
python3 init_db.py
python3 app/routes.py --port 5000 [--host 0.0.0.0] [--test-mode --timeout 10]
```

В установленном Debian-пакете используется БД `/var/lib/bird-manager/app.db`,
live-каталог `/etc/bird/live`, staged-каталог `/var/lib/bird-manager/staged`.

Пути читаются из окружения один раз при импорте процесса. Директории привязывают
`_bind_paths_from_env()`, базу — `_bind_database_from_env()`; обе функции
перевычисляют значения, если окружение изменилось, и вызываются тестом перед каждым
кейсом. Менять `BIRD_LIVE_DIR`/`DB_PATH` в живом процессе нельзя без явного вызова —
`ExecReload` у службы нет, поэтому штатный способ это перезапуск.

## Модели

| Модель | Поля |
|---|---|
| `Network` | `id`, `prefix`, `description`, `status`, `community_ids`, `enabled` |
| `Community` | `id`, `name`, `values`, `description`, `enabled` |
| `BgpPeer` | `id`, `name`, `local_as`, `neighbor`, `neighbor_as`, `status` |
| `AuditLog` | `id`, `action`, `timestamp`, `user_id`, `diff_summary` |

`enabled` — JSON boolean. Для существующих записей миграция устанавливает
`enabled=true`. `status` (`pending`/`applied`) не заменяет `enabled`.

`BgpPeer.name` и `BgpPeer.neighbor` уникальны. `create_all` не изменяет уже
существующие таблицы, поэтому при старте сервиса `ensure_schema` отдельно
проверяет наличие `UNIQUE (neighbor)` и, если индекса нет, пересобирает таблицу
в одной транзакции — колонки и значения переносятся из модели, данные не
теряются. Если в таблице уже есть дубли адресов, пересборка не выполняется:
в журнал сервиса уходит строка `[ERROR] bgp_peers: neighbor duplicates found`,
строки остаются как есть, и до их ручного разрешения правило держится только
проверка в API. Ошибка миграции печатается в журнал и откатывает транзакцию,
сервис при этом продолжает работать.

## Файлы конфигурации

SQLite — единственный и исключительный источник данных для демона BIRD. При старте и
после каждой мутации БД bird-manager перегенерирует staged-файлы; в live они попадают
только через явный Apply.

| Файл | Назначение | Редактор |
|---|---|---|
| `networks.conf` | router id, пользовательские настройки и комментарии | да |
| `bird-manager.conf` | managed include block, определяющий порядок | нет |
| `export.conf` | legacy-файл (все фильтры), генерируется для совместимости | нет |
| `routes.conf` | legacy-файл (все маршруты), генерируется для совместимости | нет |
| `core.conf` | generated `device`, `direct`, BGP protocols | нет |
| `managed-files.json` | список файлов под управлением bird-manager | нет |
| `apply_state.json` | последний reload-warning / detail | нет |
| `live-bak/` | снимок предыдущей публикации для отката | нет |
| `routes_<ASN>_<VALUE>.conf` | статические маршруты на сообщество (split layout) | нет |
| `export_peer_<имя>.conf` | export-фильтр пира (split layout) | нет |
| `export_combined.conf` | общий фильтр для пиров с `export_all` (split layout) | нет |

В пустом состоянии `networks.conf` содержит только заголовок и `router id`.

`/etc/bird/bird.conf` получает managed include block. В упакованном `.deb`
( split-режим ) `bird.conf` содержит один include:

```bird
include "/etc/bird/live/bird-manager.conf";
```

а внутри `bird-manager.conf` порядок:

```bird
include "/etc/bird/live/networks.conf";
include "/etc/bird/live/policy_*.conf";          # если есть политики
include "/etc/bird/live/export_peer_<имя>.conf";  # по каждому пиру
include "/etc/bird/live/export_combined.conf";   # если есть пир с export_all
include "/etc/bird/live/routes_<ASN>_<VALUE>.conf"; # по каждому сообществу
include "/etc/bird/live/core.conf";
```

В legacy-режиме (монолитный, без split-файлов) порядок такой же, как
раньше:

```bird
include "/etc/bird/live/networks.conf";
include "/etc/bird/live/export.conf";
include "/etc/bird/live/routes.conf";
include "/etc/bird/live/core.conf";
```

`export.conf` (legacy) и `export_peer_*.conf` (split) обязаны идти до
`core.conf`: `core.conf` ссылается на фильтры, которые определены в
export-файлах. Каждый канал BGP содержит **ровно одну** строку `export filter` —
BIRD хранит в канале один export filter, а повторная строка молча
перезаписывает предыдущую.

Имена файлов: ключ сообщества — `community_key` = `ASN_VALUE`, где `:` в
значении заменяется на `_` (например, `65500_102`). Протокол static в
соответствующем `routes_<key>.conf` называется `managed_static_routes_<key>`,
чтобы избежать `Symbol already defined` при дублировании статических маршрутов
в нескольких файлах (BIRD принимает дубли маршрутов, но не дубли filter-символов).

Фильтр свой у каждого пира:

- `export_all = false` (по умолчанию) → `export_to_<имя>`, только сети с
  community, ASN которого равен `local_as` пира;
- `export_all = true` → `export_own_networks`, все активные сети.

ASN, которого нет среди community, даёт пустой фильтр с хвостом `reject`:
пир ничего не получает, а UI показывает `ASN не найдена`.
`export_own_networks` генерируется только если хотя бы один пир включил
`export_all`.

Файлов `policy_<community_id>.conf` больше нет: их фильтры и `COMM_*` define
не использовались каналом. Старые копии удаляются из `staged` при следующей
генерации.

При изменении БД `export.conf` и include-блок обновляются автоматически.
Независимые include-строки оператора сохраняются.

`GET /api/config/overview` возвращает текущий `networks.conf`, read-only
`bird-manager.conf` и `core.conf` с diff последней публикации, а в `summary` —
список `routes.conf` и `export.conf` только с именем, путём,
признаком существования, счётчиками `+N/−N` и числом строк сравнения `rows`
(без содержимого). Ни один generated-файл нельзя редактировать или применять
через editor API: его отдаёт `GET /api/config/live` только для
`filename=networks.conf`, остальные filenames дают `400`.

`rows` — размер построчного сравнения, которое покажет панель. По нему
решается, открывать файл или оставить только счётчики: файлы с числом строк
больше 5000 не открываются вовсе, их текст не запрашивается. Для остальных
сравнение грузится отдельно через `GET /api/config/file-rows`.

Overview **не строит** строковую модель: счётчики считаются обходом того же
сопоставления, на котором строится и сама модель, поэтому число в заголовке и
строки под ним не могут разойтись. Модель собирается только по запросу —
это существенно: `export.conf` на заполненной таблице это 31 000 строк, и полный
словарь на каждый файл в каждом запросе обзора означал бы десятки тысяч
объектов ради трёх чисел.

У каждого файла есть признак `readable`. Он равен `false`, если файл существует,
но не декодируется как UTF-8: такой файл исключается из сравнения целиком
(`adds`/`dels`/`rows` равны нулю), и панель показывает «не читается» вместо
счётчика. Показывать `+0 −0` было бы опаснее, чем ничего: оператор решил бы,
что изменений нет, и Apply перезаписал бы файл. Отсутствующий файл — не то же
самое: его пустое содержимое истина, и все его строки действительно добавлены.

## Networks

### `GET /api/networks`

```json
{
  "networks": [{
    "id": 1,
    "prefix": "192.0.2.0/24",
    "description": "Office",
    "status": "pending",
    "community_ids": "[6]",
    "enabled": true
  }],
  "count": 1
}
```

### `POST /api/networks`

Обязательное поле: `prefix`.

```json
{
  "prefix": "192.0.2.0/24",
  "description": "Office",
  "status": "pending",
  "community_ids": "[6]",
  "enabled": true
}
```

Ответ `201` содержит `network`. `enabled` должен быть JSON boolean; строки
`"false"` и числа не принимаются.

Если префикс уже существует в базе, возвращается существующая запись (без
создания дубля и без audit-записи). Префикс каноникализируется перед проверкой.

`PUT /api/networks/<network_id>` частично обновляет запись. `DELETE` удаляет сеть.
`POST /api/networks/bulk/commit` принимает `enabled` для каждой записи.

### Проверка префикса: HTTP 409 и диалог подтверждения

Префикс считается корректным только если он уже канонический. `POST /api/networks`
и `PUT /api/networks/<network_id>` не правят строку молча: если префикс требует
починки или починить его нельзя, оба отвечают `409` и **ничего не записывают**.

```json
{
  "error": "Некорректный префикс",
  "needs_confirmation": true,
  "invalid": [{
    "input": "192.168.1.43/24",
    "suggestion": "192.168.1.0/24",
    "reason": "установлены биты хоста"
  }]
}
```

Правила подсказок:

| Ввод | `suggestion` | Причина |
| --- | --- | --- |
| `192.168.1.43/24` | `192.168.1.0/24` | установлены биты хоста |
| `10.9.240.0/12` | `10.0.0.0/12` | установлены биты хоста |
| `10.0.0.0/33` | `10.0.0.0/32` | недопустимая длина маски |
| `10.0.0.1` | `10.0.0.1/32` | не указана длина маски |
| `999.1.1.1/24` | `""` | некорректный адрес |

Пустой `suggestion` означает, что починить строку нельзя: она будет отброшена
в любом случае. Клиент показывает все записи разом в диалоге «Найдены
некорректные CIDR. Исправить или удалить?» и либо переотправляет подсказки,
либо добавляет только корректные префиксы.

Одно исключение: совпадение, перед которым стоит точка, молча
выбрасывается и в диалог не попадается. Регулярное выражение на
`1.2.3.4.5/24` находит внутри него `2.3.4.5/24`, но это осколок более длинной
точечной цепочки, а не префикс: чинить нечего, и показывать оператору такое
значение незачем. Проверка позиционная, поэтому работает и внутри компактного
JSON, где токен вида `{"address":"1.2.3.4.5/24"}` не отделяется разделителем.

Четыре октета против не четырёх по-прежнему различаются по значению:
`999.1.1.1/24` — это четыре октета, поэтому такая строка попадает в диалог, а
не исчезает.

Голый адрес без маски находится в двух местах: как отдельный токен
(`10.0.0.1`) и как значение ключа-адреса (`{"address":"5.63.111.80"}`). Второе
нужно потому, что в JSON такой токен не является отдельно стоящим адресом и
проверка по токену его не видит. Ключи-адреса: `address`, `cidr`, `prefix`,
`net`, `network`. Ограничение по ключам сделано намеренно, чтобы `version`
или `router_id` не превращались в префиксы. Значение с IPv6 не распознаётся:
приложение работает только с IPv4.

То же относится к префиксу с мусором за маской: `10.0.0.0/24/8` и
`10.0.0.0/24.5` отбрасываются молча, а не превращаются в `10.0.0.0/24` без
слова оператору. При этом пунктуация-обёртка (`{10.0.0.0/24}`, `(10.0.0.0/24)`,
`"10.0.0.0/24"`, `[10.0.0.0/24]`, хвостовые `.` `,` `;` `)` и конструкции вида
`ip prefix 10.0.0.0/24`) мусором не считается.

## Порядок сетей

`POST /api/networks/bulk` возвращает префиксы в порядке появления во вводе,
без повторов: один и тот же ввод всегда даёт один и тот же результат. Таблица
в диалоге дополнительно упорядочена по тексту, чтобы её было удобно читать.

Порядок строк в базе задаёт `POST /api/networks/bulk/commit`: батч
канонизируется и **вставляется отсортированным по адресу сети**, а уже
существующие строки при этом не переставляются. Ключ сортировки — пара
(версия, числовой адрес сети, длина маски), а не текст префикса: сравнение по
строке поставило бы `10.0.0.0/24` перед `10.0.0.0/8` и `100.0.0.0/8` перед
`9.0.0.0/8`.

Отсюда следствия, о которых стоит знать:

- сортируется только новый батч, весь `routes.conf` целиком не
  переупорядочивается;
- каждый импорт даёт свой отсортированный блок в конце, предыдущие блоки
  остаются на месте;
- удалённый и добавленный заново префикс окажется в конце, а не в своей
  отсортированной позиции.

Генератор конфигурации ничего не сортирует: он читает сети в порядке строк
базы, и этот порядок закреплён явным `ORDER BY id` в `get_networks`. Поэтому
порядок в `routes.conf` совпадает с порядком строк в базе — гейтвеи BGP-пиров
дописываются в конец и этой сортировке не подчиняются.

## Формат ввода

Параметр `format` у `POST /api/networks/bulk` больше не влияет на разбор
префиксов: любой ввод сканируется как текст, тем же регекспом, что и раньше
применялся панелью. Параметр сохранён для совместимости, а `command` по-прежнему
дополнительно вытаскивает имена сообществ из синтаксиса межсетевых экранов.

Причина одна: JSON-ветка требовала `dict` на верхнем уровне, поэтому массив
(`[{...}]`, то есть ровно то, чем являются готовые geo-фиды) разбирался в пустой
результат — без ошибки и без единой строки в диалоге. Фильтрация по ключам,
которую умела эта ветка, не использовалась нигде: параметр `target_keys` не
передавал никто.

Принимаются строка, список и всё остальное (объект, число) — последнее
сериализуется и сканируется как текст. Разбирать валидность JSON не нужно:
вставка geo-фида, обрезанного посередине, даёт тот же результат, что и целый,
потому что структурная целостность текстовому скану не требуется.

IPv6 не распознаётся и пропускается без следа: приложение работает только с
IPv4, генератор пишет `route … via …`.

## Импорт частями

Тело запроса ограничено `BIRD_MAX_BODY_BYTES` (по умолчанию 1 МиБ), проверка
идёт до чтения тела и действует на все маршруты, поэтому фид больше
приблизительно 13 400 адресов в JSON-форме (около 78 байт на запись) через
панель не пройдёт — придёт 413.

Панель режет ввод сама, поэтому потолка на стороне UI нет. Рез делается по
разделителям `,` `;` и пробельным символам: адрес состоит из цифр, точек и
слэша, ни один из которых в этот класс не входит, поэтому разрез сразу после
разделителя не может разрезать префикс. Учитывается и запятая: фид без единого
пробела иначе разрезался бы посреди адреса, и `10.0.0.0/24` превратился бы в
правдоподобный `10.0.0.0/2`.

Разбор идёт частями с одним диалогом на весь импорт: записи из всех частей
собираются и показываются вместе. Пока идёт работа, модальный диалог делает
панель неактивной; кнопка «Прервать» останавливает цикл перед следующим
запросом. Уже записанные части остаются, повтор безопасен — сервер пропускает
префиксы, которые уже есть.

Панель сортирует накопленный батч **до** нарезки на части записи, поэтому сами
части идут по адресу и склейка получается одним непрерывным возрастающим
рядом. Сортировка нужна именно для границ: сервер сортирует каждую полученную
часть сам, но без неё части легли бы в порядке ввода, и порядок развалился бы
ровно на стыках. Стоит около 30 мс на 50 000 префиксов против нескольких секунд
разбора, то есть это не замедление.

Ключ сортировки в браузере повторяет `network_sort_key` и обязан совпадать с
ним: биты хоста маскируются так же, `/0` обрабатывается отдельно. Расхождение
ключей не ломает запись — сервер пересортирует каждую часть, — но разваливает
порядок на границах. Оба ключа закреплены тестом, который прогоняет JS-функцию
через node и сверяет с Python на наборе крайних случаев.

Части записи идут по 6000 записей (около 650 Киб тела). Каждый запрос
сортируется сервером отдельно, поэтому большой импорт даёт **по одному
отсортированному блоку на часть**, но при согласованных ключах эти блоки идут
подряд по адресу, а не вразнобой.

`POST /api/networks/bulk` использует тот же контракт: `parsed_networks` содержит
только уже канонические префиксы, а `invalid` — список объектов
`{input, suggestion, reason}` для диалога. Запись этим запросом не выполняется.

Второй рубеж стоит в слое CRUD: `create_network`, `update_network` и
`bulk_commit_networks` канонизируют префикс перед записью, поэтому в базе не
может оказаться неканоничный префикс даже при прямом обращении к API. Благодаря
этому дедупликация в `bulk_commit_networks` схлопывает `10.9.240.0/12` и
`10.0.0.0/12` в одну запись. Ответ `bulk/commit` содержит
`skipped_invalid` — сколько записей отброшено сервером как нечитаемые.

## Communities

### `GET /api/communities`

```json
{
  "communities": [{
    "id": 6,
    "name": "65500:102",
    "values": "65500:102",
    "description": "Site policy",
    "enabled": true
  }],
  "count": 1
}
```

### `POST /api/communities`

Обязательное поле: `name`, поле `enabled` по умолчанию `true`.

Имя — источник истины: оно решает, в какое ведро экспорта попадут префиксы
этого сообщества и какой меткой они будут помечены.

| Форма `name` | ASN | значение |
| --- | --- | --- |
| `65500:102` | 64512…65534 | 1…65280 |
| `65500` (без двоеточия) | 64512…65534 | необязательно |

Значение `0` в форме `ASN:VALUE` **зарезервировано** за формой без сообщества:
`65534:0` отвергается, а голое `65534` само разворачивается в `65534:0`. Так
дефолтное сообщество записывается однозначно, а руками `0` не вводится.

Если `values` не передан, он берётся из имени. Это делает запись
самодостаточной: переименование сообщества больше не меняет метку молча,
потому что значение уже лежит в базе.

Диапазоны: приватный ASN по RFC 5398 (16-битный), значение 0…65280 —
`65535` это No Community по RFC 1997 и анонсировать его нельзя. Ошибка —
`400` с текстом.

`values` принимает и список через запятую. Голое число в `values` читается как
**значение под ASN 65534**, а не как ASN: `100` — это `(65534, 100)`. Это
чтение задано самим `_community_pairs`, и тест его закрепляет.

Community без включённых сетей автоматически переводится в `enabled=false` при
следующей регенерации. Community может иметь values из нескольких пар.
`65534` — каноническая Community default: пустые `community_ids` сетей
приводятся к её ID, а описание автоматически устанавливается в `default`.
Её `values` равно `65534:0`, то есть та же пара `(65534, 0)`, что давало прежнее
голое `0`, — запись только переписана в форму, которую переименование узнаёт.

`POST /api/communities` при существующем имени возвращает существующую запись
со статусом `200` (не `201`), без создания дубля.

### `PUT /api/communities/<community_id>`

`name` и `values` проходят ту же проверку, что и при создании. `values`
обновляется при смене имени **только если оно было получено из старого имени** —
такое значение ничего о себе не говорит и пересчитывается из нового. Значение,
заданное вручную, и список значений сохраняются.

Переименование на уже занятое имя возвращает `409` с `code: duplicate_community_name`.

Имя не обязано быть `values` копией в обоих направлениях, но после
переименования сменить ASN — значит перенести префиксы сообщества из фильтра
одного пира в фильтр другого. Ничего из этого не применяется само: смена
видна в диффе на вкладке BIRD.

`DELETE /api/communities/<community_id>` каскадно удаляет все связанные Network-записи,
их policy-ссылки и generated-файлы.

## BGP peers

### `GET /api/bgp_peers`

Возвращает `{ "bgp_peers": [...], "count": N }`. Каждый элемент:

| Поле | Смысл |
|---|---|
| `id`, `name`, `local_as`, `neighbor`, `neighbor_as`, `status` | как в БД |
| `export_all` | `true` — пир получает все активные сети; `false` (по умолчанию) — только сети своего ASN |
| `export_count` | сколько префиксов попадёт в фильтр пира при `export_all = false` |
| `asn_found` | есть ли среди community хоть одна сеть с ASN пира |
| `router_id` | адрес, который BIRD использует как router id — из него формируется `remote.address` в конфиге RouterOS |

`export_count` и `asn_found` считаются по тем же данным, что и генератор, так
что цифра в UI совпадает с содержимым `export.conf`.

### Панель пиров в интерфейсе

Список пиров находится на вкладке `Сети` рядом с деревом сетей, обе панели
занимают по половине ширины. Панель свёрнута при первой загрузке и показывает
только счётчик (`GET /api/bgp_peers/count`); список подтягивается лениво при
первом раскрытии и показывает данные базы — `peer id`, `Local AS`, `Neighbor`,
`Neighbor AS`, `status` и удаление. Под именем показывается объём выдачи:
`все сети` при `export_all`, `N префиксов` при совпавшем ASN или `ASN не
найдена`, если ни одна сеть не несёт community с этим ASN. Форма добавления
содержит галочку «Экспортировать все сети» и подсказку, что по умолчанию пир
получает только сети своего ASN.

Живое состояние канала и префиксов в этой
панели не выводится: оно остаётся в блоке «BIRD peers» на вкладке `Система`,
который читает `birdc`.

### `GET /api/bgp_peers/count`

Возвращает `{ "count": N }` без содержимого — по образцу
`GET /api/networks/count`. Панель «BGP peers» на вкладке «Сети» стартует
свёрнутой и показывает только счётчик, поэтому список грузится лениво при
первом раскрытии. Маршрут не конфликтует с
`/api/bgp_peers/<peer_id>`: шаблоны якорены, а `count` не является числом.

### `POST /api/bgp_peers`

| Поле | Проверка |
|---|---|
| `name` | BIRD-идентификатор: буква или `_` первым символом, далее буквы/цифры/`_`, максимум 255 символов |
| `neighbor` | строгий IPv4 без `/mask`; **уникален** среди peers и в live/staged конфиге |
| `neighbor_as` | ASN 1–4294967295; **уникален** среди peers и в live/staged конфиге |
| `local_as` | ASN 1–4294967295, по умолчанию `65500` |
| `status` | по умолчанию `active` |
| `export_all` | булево, по умолчанию `false` |

Оба правила уникальности проверяются по БД и по сырому тексту `core.conf` и
`networks.conf` в live и staged, поэтому вручную добавленный блок `protocol bgp`
тоже учитывается. Занятый адрес или занятый ASN дают `400` с текстом
«уже используется другим пиром (peer id / конфиг)».

Один адрес — один peer намеренно. Два `protocol bgp` на один `neighbor` BIRD
принимает без ошибки: для исходящих соединений у каждого свой сокет с
эфемерным локальным портом, поэтому конфликта на уровне демона не возникает.
Но и Established не будет — удалённый роутер определяет соседа по адресу, а не
по порту источника, и второй OPEN с другим `remote AS` не совпадёт с его
конфигурацией. На входящей стороне BIRD отдаёт сессию первому подошедшему
listen-request (`bgp_find_proto`), так что второй протокол на тот же адрес не
получит соединение никогда. Панель отказывает на этапе API, вместо того чтобы
публиковать конфиг, который тихо не поднимется. Если провайдер действительно
держит несколько сессий к одному адресу, они различаются портами
(`local port`, `neighbor ... port`) — эти поля панель не поддерживает.

Уникальность адреса закреплена также на уровне БД (`UNIQUE (neighbor)`), что
закрывает гонку двух одновременных `POST`: `IntegrityError` возвращается тем же
`400`, а не `500`.

### `DELETE /api/bgp_peers/<peer_id>`

Удаляет запись и перегенерирует staged-файлы.

### Поле `export_all`

По умолчанию `false`, и это меняет смысл сессии: пир получает только те сети,
у которых есть BGP community с ASN, равным его `local_as`. Например, пир с
`local_as = 64600` не получит ни одной из 7817 сетей с community `65500:*`.

Если среди community нет ни одной сети с ASN пира, его фильтр пуст и
заканчивается `reject` — пир не получает ничего. Это осознанно: молчаливый
откат к полной таблице отдал бы клиенту чужую транзитную информацию, а пустой
отдаваемый набор виден в панели и в `birdc` сразу.

`true` переводит пира на общий фильтр `export_own_networks` со всеми активными
сетями и всеми их community.

## Конфигурационный lifecycle

### `POST /api/config/generate`

Читает snapshot БД, генерирует staged `networks.conf`, `bird-manager.conf`,
`export.conf`, `routes.conf`, `core.conf`, а также split-файлы
`routes_<ASN>_<VALUE>.conf`, `export_peer_<имя>.conf` и
`export_combined.conf` (если есть пир с `export_all`), валидирует bundle через
`bird -p`. Live публикуется только через Apply;
`/etc/bird/bird.conf` не изменяется. Legacy `export.conf` и `routes.conf`
генерируются для совместимости, но в split-режиме (по умолчанию в .deb) не
включены в `bird-manager.conf`.

Ответ:

```json
{
  "status": "success",
  "config_path": "/var/lib/bird-manager/staged/networks.conf"
}
```

### `GET /api/config/live` и `/api/config/staged`

Редактор работает только с `networks.conf` и возвращает его текст.
Generated-файлы не возвращаются в редактор.

### `GET /api/config/diff/all`

Возвращает diff по всему сгенерированному bundle: `networks.conf`,
`routes.conf`, `routes_<ASN>_<VALUE>.conf`, `core.conf`,
`export.conf`, `export_peer_<имя>.conf`, `export_combined.conf` и
`bird-manager.conf`. Файлы вне bundle (backups, временные файлы) в listing не
попадают. В split-режиме префиксы живут в `routes_<ASN>_<VALUE>.conf`, а
фильтры пиров — в `export_peer_<имя>.conf`.

### `GET /api/config/file-rows`

Только чтение. Построчное сравнение одного файла bundle: live слева, staged
справа. Панель грузит его при раскрытии секции.

| Параметр | Значение |
|---|---|
| `filename` | `networks.conf`, `routes.conf`, `core.conf`, `export.conf`, `bird-manager.conf`, а также `routes_<ASN>_<VALUE>.conf`, `export_peer_<имя>.conf` или `export_combined.conf` |

```json
{
  "filename": "core.conf",
  "adds": 0,
  "dels": 8,
  "total_rows": 20,
  "returned_rows": 20,
  "truncated": false,
  "rows": [
    {"old": "# Device", "new": "# Device", "kind": "context"},
    {"old": "protocol bgp main_mkt {", "new": null, "kind": "removed"}
  ]
}
```

`kind` — `context` (совпадает), `changed` (строка изменена), `added` (есть
только в staged), `removed` (есть только в live; в `new` стоит `null`, и это не
то же самое, что пустая строка). Обе стороны всегда содержат одинаковое число
строк, поэтому колонки выравниваются по индексу, а не расчётом. Изменённая
строка считается и как добавление, и как удаление — так же, как в unified diff.

`adds`, `dels` и `total_rows` точны всегда; обрезается только `rows` (не более
2000), о чём сообщает `truncated`. Панель при этом не спрашивает файл вовсе,
если `rows` из overview больше 5000. Для файла, который не читается как UTF-8,
возвращается `readable: false` с пустым `rows`.

### `GET /api/config/file-diff`

Только чтение. Unified diff одного файла bundle по запросу.

| Параметр | Значение |
|---|---|
| `filename` | `networks.conf`, `routes.conf`, `core.conf`, `export.conf`, `bird-manager.conf`, а также `routes_<ASN>_<VALUE>.conf`, `export_peer_<имя>.conf` или `export_combined.conf` |

Имя проверяется по списку файлов bundle, поэтому путь из запроса не может
попасть на диск. Ответ:

```json
{
  "filename": "routes.conf",
  "adds": 0,
  "dels": 7818,
  "total_lines": 7824,
  "returned_lines": 400,
  "truncated": true,
  "diff": "--- live\n+++ staged\n@@ -1,7821 +1,3 @@\n..."
}
```

`adds`/`dels` и `total_lines` всегда точные — это и есть предупреждение о
потере маршрутов. Обрезается только текст: максимум 400 строк и 64 КиБ,
фактический размер виден в `total_lines`.

### `POST /api/config/preview`

Body:

```json
{
  "filename": "networks.conf",
  "content": "# BIRD IP Config\n..."
}
```

В split-режиме preview не добавляет policy/routes/core строки в editor, но
создаёт **ghost-строки**: строки live, которых нет в редактируемом тексте,
попадают в модель как `removed`, чтобы колонки оставались выровненными по
индексу и оператор видел, что именно его правка удалила. `editor_content`
остаётся пользовательским текстом, а сравнение относится только к
`networks.conf`.

Ответ (без `changes`: счётчики панель берёт из `/api/config/overview`, а модель
строк — отсюда):

```json
{
  "filename": "networks.conf",
  "editor_content": "# test\nprotocol static x {\n    ipv4;\n}\n",
  "merged": false,
  "diff": "--- live\n+++ staged\n@@ ...",
  "rows": [
    {"old": "# BIRD IP Config", "new": "# test", "kind": "changed"},
    {"old": "# Local AS: 65500", "new": "protocol static x {", "kind": "changed"},
    {"old": "# 10.0.0.0/8", "new": null, "kind": "removed"}
  ],
  "syntax": {"valid": true, "errors": [], "error_lines": [], "error_files": [],
             "warnings": [], "summary": "ok"},
  "syntax_error_rows": []
}
```

`rows` использует тот же формат, что и `GET /api/config/file-rows`
(`old`/`new`/`kind`), но без обрезки: в редакторе показываются все строки
пользовательского текста. `diff` — текстовый unified diff, он оставлен для
сторонних клиентов; панель его не использует.

Проверка синтаксиса парсит **весь bundle** через тот же include-блок, что и
публикуемый entrypoint и Apply (`ConfigManager._validation_include_block`), с
единственной подменой — include `networks.conf` на редактируемый текст.
Список include не дублируется в коде превью.

Ответ `syntax` содержит `valid`, `errors`, `error_lines`, `error_files`,
`warnings`, `summary`. Поле `error_files` параллельно `errors` и указывает,
какому файлу bundle принадлежит ошибка (`null` — ошибка пришла от regex-проверок
самого текста).

`syntax_error_rows` содержит строки редактора **только** для ошибок в
`networks.conf`. Номер строки из `bird -p` может относиться к `core.conf`,
`export.conf` или `routes.conf`; такой номер не маппится в
редактор, потому что в редактируемом файле этой строки нет. Такая ошибка
показывается текстом с именем файла, но полосу в редакторе не рисует.

### `POST /api/config/apply`

Применяет полный staged bundle, атомарно публикует файлы, выполняет
`birdc configure` и пишет audit. Снимок предыдущей публикации для отката
хранится в `/var/lib/bird-manager/live-bak` (настраивается
`BIRD_PUBLISH_BAK_DIR`): в `/etc/bird/live` не остаётся ни `*.bak`, ни `*.tmp`,
поэтому там лежат только файлы, которые читает BIRD. Main `bird.conf` не
изменяется.

При ошибке валидации ответ дополнительно содержит `editor_content` и
`error_rows` — строки редактора с учётом правила «только свой файл»
(см. описание preview).

При успешной публикации ответ содержит:

- `applied_networks` — список префиксов, статус которых изменился на этом Apply
  (pending → applied или applied → pending, если сеть отключена/удалена);
- `audit_id` — ID записи в audit log;
- `diff` — сводный diff по bundle;
- `files` — список опубликованных файлов (split layout);
- `reload_warning`, `reload_detail` — результат reload BIRD;
- `live_content` (только при вызове с `content`) — выровненный текст редактора.

Ответы:

- `success` — published/reload успешен;
- `success_with_warning` — файлы опубликованы, но reload дал warning;
- `degraded` — bundle/reload требует внимания;
- `error` — валидация или публикация не выполнены.

### Status и health

`GET /api/config/status?filename=networks.conf` возвращает `status`, `action`,
`user_id`, `last_applied`, `last_diff_summary`, `has_backup` (есть ли снимок для
отката), `bird_running`, `reload_warning`, `reload_detail`, реальные
`bird_last_reboot` и `bird_last_reconfiguration` из `birdc show status` и объект
`backup` со `retention`, `used`, `free`, `slots` и отсортированным списком
`items`. Элемент содержит безопасный `id`, `created_at`, `display_time`,
`legacy_time`, `size` и признак `latest`.
### `GET /api/bird/protocols`

Read-only снимок `birdc show protocols all`. Классификация идёт по колонке
`Proto`: любой `BGP` попадает в `peers` (включая протоколы, добавленные в
`bird.conf` вручную), всё остальное — в `service`.

Верхний уровень: `status` (`ok`/`error`), `bird_running`, `error`, `peers`,
`service`.

Поля пира:

| Поле | Источник |
|---|---|
| `name` | имя протокола |
| `state` | сводная колонка `State` (FSM) |
| `bgp_state` | детальная строка `BGP state:` |
| `channel_state` | `State` блока `Channel ipv4` |
| `neighbor`, `neighbor_as`, `local_as` | детальный блок BGP |
| `since` | колонка `Since` как есть: дата (`2026-09-25`), дата со временем (`2026-09-26 12:04:11`) или голое время с миллисекундами (`10:08:14.529`) — BIRD печатает последнее для протоколов, запущенных сегодня |
| `info` | хвост колонки `Info` (может быть пустым) |
| `last_error` | строка `Last error:` либо `null` |
| `imported`, `exported` | счётчики `Routes: N imported, M exported` (rx/tx) |
| `managed` | есть ли протокол в peer-списке панели |
| `in_bird` | `false`, если пира нет в выводе BIRD |

`state`, `bgp_state` и `channel_state` различаются намеренно: канал может быть
не поднят при активной FSM-сессии. `imported`/`exported` равны `null`, когда
BIRD не печатает `Routes:` — так ведёт себя неустановленная сессия, и это не
то же самое, что ноль.

Поля `service`: `name`, `proto`, `state`, `channel_state`, `import_state`,
`since`.

Пир, настроенный в панели, но отсутствующий в выводе BIRD, добавляется с
`in_bird: false` — но только когда BIRD ответил: при недоступном демоне
`status: error`, и `peers`/`service` пустые.

`POST /api/bird/reload` выполняет `birdc configure` и пишет audit
`BIRD_RECONFIGURE`. Ответ всегда `200`: `status` (`ok`/`error`), `bird_running`
и `error` (текст сбоя). Такой контракт выбран намеренно — панель показывает
причину сбоя перезагрузки как текст, а не как код ответа.

`GET /api/health` возвращает `healthy` либо `degraded` с `reload_warning` и
`reload_detail`.

## Backup

Backup API работает с полными snapshot. В архив входят:

| Путь в архиве | Что это |
|---|---|
| `db/app.db` | SQLite — единственный и исключительный источник данных для демона BIRD |
| `staged/` | весь staged-каталог |
| `live/` | весь live-каталог |
| `state/managed-files.json` | манифест файлов под управлением |
| `main/bird.conf` | main-конфиг только для offline recovery |

Снимок для отката (`live-bak/`) в архив **не** входит: это состояние
предыдущей публикации на диске, оно пересоздаётся при каждом Apply. В
`/etc/bird/live` файлов отката нет вовсе — только то, что читает BIRD.

## Контроль доступа

Проверка выполняется в WSGI-входе до роутинга и до чтения тела запроса.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BIRD_TRUSTED_SOURCES` | `auto,127.0.0.1/32,::1/128` | список CIDR; `auto` — сеть основного IPv4-интерфейса хоста |
| `BIRD_TRUSTED_PROXIES` | пусто | прокси, чьему `X-Forwarded-For` можно верить; заголовок учитывается **только** если сам peer (REMOTE_ADDR) входит в список, при пустом значении заголовок игнорируется полностью |
| `BIRD_TRUSTED_ORIGINS` | пусто | при непустом значении POST/PUT/DELETE/PATCH без совпадающего `Origin` получают `403`. Токены — `scheme://host` без trailing slash, сравнение case-insensitive, разделители `,` и `;` |
| `BIRD_MAX_BODY_BYTES` | `1048576` | превышение даёт `413`, тело не читается |
| `BIRD_DEBUG_ERRORS` | `0` | `1` добавляет текст исключения в 5xx-ответы |
| `APP_HOST` | `0.0.0.0` | адрес привязки (и `--host` в CLI) |

Эффективная политика печатается при старте сервиса строкой `[ACCESS]`.

## Коды ответа

| Код | Когда |
|---|---|
| `400` | ошибка валидации полей или попытка редактировать не-`networks.conf` файл |
| `403` | источник вне `BIRD_TRUSTED_SOURCES`, недоверенный proxy для `X-Forwarded-For`, либо мутирующий запрос без совпадающего `Origin` при заданном `BIRD_TRUSTED_ORIGINS` |
| `404` | неизвестный путь **или** неподдерживаемый метод для известного пути: роутер не различает эти случаи, `405` не возвращается |
| `413` | тело запроса больше `BIRD_MAX_BODY_BYTES` (тело не читается) |
| `500` | внутренняя ошибка; текст исключения попадает в ответ только при `BIRD_DEBUG_ERRORS=1`, иначе возвращается generic-сообщение |

Все ответы содержат `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: no-referrer`, строгий `Content-Security-Policy` и
`Cache-Control: no-store`.

Поля `code` в телах ошибок (например `invalid_prefix`, `duplicate_community_name`,
`missing_prefix`, `enabled_not_boolean`, `network_not_found`, `community_not_found`,
`editable_only_networks_conf`, `unknown_bundle_file`, `missing_name`,
`bgp_peer_not_found`, `server_error`) используются фронтендом для перевода через
ключи `err.*` в `i18n.js`. Полный список — в `app/routes.py` (поиск `return ... 'code':`).

Тела от 16 КиБ сжимаются gzip, если клиент прислал `Accept-Encoding: gzip`;
в этом случае добавляются `Content-Encoding: gzip` и
`Vary: Accept-Encoding`. Полный список сетей — 963 КиБ и сжимается до 66 КиБ.
Access-лог при этом продолжает писать **исходный** размер, чтобы строка
журнала значила то же, что и раньше.

`POST /api/backup` создаёт snapshot и применяет локальную ротацию.
`BIRD_BACKUP_RETENTION` задаёт число слотов (по умолчанию 5, диапазон
1–99). `POST /api/backup/restore` сохраняет совместимое восстановление самого
нового архива. `POST /api/backup/<backup_id>/restore` восстанавливает конкретный
архив, а `DELETE /api/backup/<backup_id>` удаляет его. Идентификаторы допускают только
`latest` или строку `YYYYMMDD-HHMMSS-microseconds`; файловые пути из API не
принимаются.

Main `bird.conf` остаётся в архиве только для offline recovery и не
восстанавливается поверх текущего файла. Старые archive без
`bird-manager.conf` получают его из restored live bundle. Выбранный archive
до замены state проходит `bird -p`; после restore выполняется `birdc
configure`.

## Audit

Actions: `CREATE_NETWORK`, `UPDATE_NETWORK`, `DELETE_NETWORK`,
`CREATE_COMMUNITY`, `UPDATE_COMMUNITY`, `DELETE_COMMUNITY`, `CREATE_BGP_PEER`,
`DELETE_BGP_PEER`, `BULK_IMPORT_NETWORKS` (разбор), `BULK_IMPORT_COMMIT`
(запись), `APPLY_CONFIG`, `ROLLBACK_CONFIG`, `BIRD_RECONFIGURE`, `BACKUP`,
`RESTORE_BACKUP`, `DELETE_BACKUP`.

`diff_summary` при публикации всего bundle содержит сначала строку с точными
счётчиками по каждому изменившемуся файлу (`routes.conf +0 -7818; core.conf +0
-8`), затем первые 40 строк diff. Полный текст не пишется: у заполненного
bundle он достигает мегабайта, а именно счётчики читает оператор перед
публикацией. Полный diff по одному файлу доступен через
`GET /api/config/file-diff`.
